# План: сфера Project management (workspace `board`)

> Цель — чтобы PM работал так же end-to-end, как Sales: онбординг → кейс → разбор → сертификат.
> Архитектура уже готова к новой сфере (field packs, плагины workspace, общий event log). Ниже — что именно добавить и в каком порядке.

## 1. Чем PM-кейс отличается от Sales

| | Sales (`chat`) | Project management (`board`) |
|---|---|---|
| Собеседники | 1 персонаж (weekly — до 2) | **3 стейкхолдера** с конфликтующими целями |
| Ход пользователя | Сообщение | Сообщение **или действие на доске**: перенести задачу, сменить приоритет, сдвинуть дату, срезать скоуп |
| Главное напряжение | Доверие клиента | Баланс: доверие каждого стейкхолдера + сроки + скоуп |
| Типичные повороты | Письмо от CFO | Скоуп-крип, ключевой инженер заболел, дедлайн сдвинули, баг в проде |
| Исход | Deal won / lost / Client left | Plan approved / Plan rejected / Escalated |

Пример кейса: запуск фичи через 3 недели. Head of Sales хочет всё к конференции, Engineering lead говорит, что половина нереальна, Finance режет бюджет на подрядчика. У пользователя доска из 14 задач, таймлайн и чат с каждым. Нужно согласовать реалистичный план к концу кейса.

## 2. Что менять по слоям

### Контракты (`src/contracts`) — договориться втроём в первую очередь
- `events.ts`: новый тип события `board_action` с `meta: { action: 'move' | 'reprioritize' | 'reschedule' | 'cut' | 'assign', taskId, from, to }`. Ходом считается и сообщение, и действие на доске.
- `docs.ts`: новый `kind: 'board'` — `{ columns: [{id,title}], tasks: [{id,title,estimateDays,owner,priority,columnId,dependsOn[]}], milestones: [{id,title,date}] }`.
- `case.ts`: исход для PM — `approved | rejected | escalated` (или общий `won/lost/left` с подписью по сфере в UI — проще, контракт не меняется).
- `persona_state` уже хранится на персонажа — подходит для трёх стейкхолдеров без изменений.

### Field pack `src/field-packs/project_management`
- `pack.json`: subfields `project_manager`, `delivery_manager`, `product_manager`; workspace `board`; измерения навыков: `prioritization`, `stakeholder_alignment`, `risk_communication`, `scope_negotiation`, `critical_ai_use`.
- 10–12 архетипов с тегами `focus` (как у Sales, см. `src/contracts/focus.ts` — добавить PM-теги: `prioritization`, `scope_creep`, `conflicting_stakeholders`, `deadline_pressure`, `budget_cut`, `risk_escalation`, `status_reporting`).
- 3 demo-кейса (по одному на подсферу) — для демо-режима и на случай падения LLM.
- Персонажи-шаблоны: Head of Sales, Engineering lead, Finance partner, Design lead, CTO, Client sponsor.

### Бэкенд (`src/modules`)
- `case-engine`: генерация с 3 персонажами и документом `board`. Отдельный промпт `case.generate.pm.v1.md` (проще, чем ветвить общий).
- `simulation`: обработка `board_action` — детерминированно применить к состоянию доски, затем каждому затронутому стейкхолдеру отдать событие для реакции (`persona.reply` уже умеет; добавить в вход описание изменения доски).
- `simulation`, director: твисты для PM — по ходу или по состоянию доски (например, «критическая задача без владельца после хода 4»).
- `evaluation`: размечать и `board_action`, промпт `eval.moves` получает состояние доски до/после. Accuracy считается так же.
- `credentials`: сертификат без изменений, навык из PM-измерений.

### Фронтенд
- `src/workspaces/board/` — новый плагин по интерфейсу `WorkspacePlugin` (`src/workspaces/types.ts`):
  - слева — доска: колонки `Now / Next / Later / Cut`, перетаскивание (dnd-kit), смена приоритета и даты из меню карточки; полоска таймлайна с милстоунами сверху;
  - центр — чат с выбранным стейкхолдером, переключатель из трёх аватаров с индикатором доверия каждого;
  - справа — Copilot, как в chat;
  - каждое действие на доске — оптимистичное обновление + POST, как сообщения.
- Онбординг: включить карточку Project management, роли — из `subfields` PM, чипы фокуса — PM-теги.
- Review и сертификат: в таймлайне ходов действия на доске показываются с иконкой и описанием («Moved “SSO” to Later»). Кривая доверия — три линии, по одной на стейкхолдера.

## 3. Порядок работ и оценка

| # | Задача | Кто | Оценка |
|---|---|---|---|
| 1 | Контракты: `board_action`, doc `board`, PM-теги фокуса | все трое | 1 ч |
| 2 | Field pack: pack.json, 10 архетипов, 6 персонажей, 3 demo-кейса | backend | 3 ч |
| 3 | Генерация PM-кейса (промпт + валидация доски) | backend | 3 ч |
| 4 | Плагин `board`: доска, таймлайн, чат с тремя, Copilot | frontend + design | 6 ч |
| 5 | Simulation: `board_action`, реакции стейкхолдеров, твисты | backend | 4 ч |
| 6 | Evaluation и Review для действий на доске, три кривые доверия | backend + design | 3 ч |
| 7 | Онбординг и дашборд для PM, e2e-тест одного кейса | frontend | 2 ч |

Итого ~22 часа работы, параллельно втроём — 8–10 часов календарного времени. Шаги 2–3 и 4 идут параллельно после шага 1, потому что фронт работает на demo-кейсе из шага 2.

## 4. Риски
- **Длина генерации.** Три персонажа и доска — промпт больше, генерация может уйти за 2 минуты. Решение: пул заранее сгенерированных онбординг-кейсов (как `seed:onboarding` для Sales) и параллельная генерация рубрики.
- **Оценка действий на доске.** LLM хуже размечает «перенёс задачу», чем текст. Решение: в рубрике явные ожидаемые действия (`expectedBoardActions`) и детерминированная проверка, LLM только объясняет.
- **Сложность UI.** Если не успеваем — урезать до доски без drag-and-drop (действия из меню карточки), таймлайн только для чтения.

## 5. Минимальная версия для питча
Если времени мало: шаги 1, 2 (только demo-кейсы), 4 (без перетаскивания) и упрощённый 5 (без твистов). Тогда PM-кейс проходится целиком на demo-данных, а генерация под профиль остаётся следующим шагом.
